# Oak lesson authoring guide (AUTHORING)

For every agent or person who writes or reviews Oak content. It applies `docs/design/contracts.md` (schemas, budgets, IDs, unlocks, grading) and `content/STYLE.md` (the code dialect). If this guide and those disagree, they win; fix this guide.

The tools named here (`content:check`, `content:build`, the `theory` CLI, `/dev/listen`) are delivered in Wave 1; this guide is their specification from the author's side.

## 1. How content gets made

Content is authored **just in time**: always at least two units ahead of the learner, never the whole course up front. One unit goes through this pipeline:

1. **Unit spec.** Take the unit's rows from contracts §2 (lesson IDs, titles, objectives, skills) and its unlocks from contracts §3.2. Check that every tool a lesson needs is unlocked at or before it in every legal order (contracts §7.6; for a track or side lesson the default order is not enough), and that every skill's prerequisites come earlier (contracts §4.2). Nothing in a lesson may contradict those tables; to change them, change contracts first.
2. **Author.** One agent per lesson, starting from this guide, STYLE and the two exemplar lessons (`content/core/U01/L01`, `content/core/U03/L02`). Loop on `bun run content:check <lessonId>` until it is green.
3. **Music-theory review** (adversarial, §9.2).
4. **Playtest** (an agent that solves each step using only what earlier lessons taught, §9.3).
5. **Listen QA** on `/dev/listen`: a human hears new or changed **shown examples and reference solutions** only (§9.4).
6. **Merge**: green checks, then one commit.

Drills, fact cards and ladder levels L1–L4 are generated by code. You write lessons, checkpoints' authored items, capstone briefs, Band layers and repertoire entries.

A lesson is two files in `content/core/Uxx/Lyy/` (or `content/advanced/J1/L03/`):

- `lesson.ts`: the typed truth. Metadata, steps, every piece of code, every exercise, grading, tests.
- `lesson.mdx`: prose only. One `<Step id="S3">` block per step. No code fences, no numbers that grading depends on, no unlock or skill declarations.

## 2. The lesson template

Every lesson is **Predict → Run → Investigate → Modify → Make** (PRIMM), ordered **sound → code → symbol**, and ends with a saved sketch. The default order of step kinds is:

`listen → predict → run → investigate → see → modify → (ear | sing | tap) → make`

| PRIMM stage | Step kind | Exercise kind (contracts §5.8) | What the learner does | Graded? |
|---|---|---|---|---|
| sound first | `listen` | `ListenEx` | plays a loop, just listens | no (completes on one full loop) |
| **Predict** | `predict` | `PredictEx` (`hum`, `choose` or `count`) | hums or picks what the code will sound like, before running it | never gates; logged |
| **Run** | `run` | `RunInvestigateEx` with no questions | runs the code, sees the prediction against the result | no |
| **Investigate** | `investigate` | `RunInvestigateEx` | toggles layers, clicks the token or note that does X | light (predicate targets) |
| symbol | `see` | none | sees the staff or the term for what was just heard | no |
| explain | `concept` | none | reads a card of ≤ 120 words with 1–2 audio examples | no |
| **Modify** | `modify` | `CodeModifyEx`, `CodeFillEx`, `ErrorHuntEx` | changes the code to hit a target | **yes** |
| Modify (variant) | `parsons` | `ParsonsEx` | orders chord or bar blocks | yes |
| retrieval | `quiz` | `FactEx`, `KeyboardEx`, `StaffReadEx` | answers one fact | yes |
| ear | `ear` | `IdentifyEx`, `DictationEx` (generator stimulus) | a mini-set that introduces a drill family | yes → SRS |
| voice | `sing` | `SingEx` (must declare `fallback`) | sings a pitch, degree or echo | yes → SRS; never gates |
| pulse | `tap` | `TapEx` | taps along, echoes or reads a rhythm | yes → SRS; never gates |
| dictation | `dictate` | `DictationEx`, `TranscribeStepEx` | writes down what was heard | yes |
| writing | `notate` | `StaffWriteEx` | writes notes on the staff | yes |
| judgement | `compare` | `IdentifyEx` (two audio cards) | A/B: which ends more conclusively? | light |
| **Make** | `make` | `CodeMakeEx` | writes a 2–8 bar sketch over the Band and saves it | one required rule; never blocks saving |
| metacognition | `reflect` | none | rates a can-do statement | no |

Rules of the template:

1. **Sound → code → symbol inside every concept.** The learner hears or plays the thing, then reads or writes its code, and only then meets the staff view or the term. A term never appears before its sound.
2. A lesson teaches **one idea**. Its title names the idea; its `objective` is one sentence the learner could say afterwards.
3. `predict` comes before the first `run` of new material and asks for an inner-hearing guess (hum it, or choose).
4. Repeat Modify rather than adding a new concept. Two small Modify steps beat one large one.
5. The **last step is `make`**. From U01 on it plays over a Band layer (§7).
6. The warm-up and the Coda are engine-driven. Do not author review or wrap steps. Do not author a first drill set or first sing for a new family inside the lesson unless the budget still holds: by default the lesson **seeds** the family (`srs: [{ family, mode: 'seed' }]`) and the engine runs its blocked-intro sets in tomorrow's warm-up.
7. Mark a step `testOut` only when it is pure code mechanics (a mini-notation operator, `setcpm`, labels) that a programmer may already know (contracts §9.5).
8. Choose `wrapAt`: the step after which the learner has made something that stands alone. It is where a 15-minute session stops for the day.

## 3. Budgets (content CI enforces all of them)

| Limit | Value |
|---|---|
| Lesson content at the 20-minute target (New + Make) | **13 minutes** after scaling |
| Scaling | every `step.minutes` is your **expert** estimate, in steps of 0.25; CI multiplies by **1.4**. Your own numbers must add up to ≤ **9.25** |
| Steps | ≤ **12** |
| Graded checks (`graded: true`) | ≤ **3** (an `AllEx` counts once; the Make's required rule does not count) |
| New terms | ≤ **3** (an antonym pair introduced together counts as one) |
| Panels per step in U00–U04 | at most **2 of {roll, staff, keyboard}** |
| Make | 2–8 bars, ≈ 2.5–3 expert minutes, exactly **one** `required` rule |
| Split for the 15-minute target | scaled part A (up to `wrapAt`) ≤ 8.5 min; scaled part B ≤ 9.5 min |
| Optional stretch steps (`optional: true`, 25-minute target only) | ≤ 5 scaled minutes in total |
| Prompt length | ≤ 60 words; concept cards ≤ 120 words |

Typical expert minutes: listen 0.5; predict 0.5–1; run 0.5; investigate 1; see 0.5; concept 1; modify 1–1.5; quiz 0.5; ear mini-set 2; sing 1.5; tap 1.5; make 2.5–3. If the lesson does not fit, cut scope or ask for a split in contracts §2; never shave the estimates.

Each unit from U02 on contains at least one **"Play from the page"** step: a `modify` or `dictate` step whose starter is staff-only (no code, no roll), answered in code.

## 4. Voice and microcopy

Write to one adult programmer who is new to music. Second person, short sentences, musical verbs, no hype.

| Do | Do not |
|---|---|
| "Press Play and nod along." | "Let's dive into the wonderful world of rhythm!" |
| "Not quite: bars 2 and 4 differ. Listen to bar 2 again?" | "Wrong!" / "Oops!" / any exclamation mark on a failure |
| "That's it: 5 4 3 2 1. The tune walks home." (specific) | "Great job!" (generic praise) |
| "Hear how 7 leans up to 1." (sound first) | "The leading tone resolves to the tonic by semitone." (term first) |
| "degree 5 (G)" (degree first, letter in brackets) | "G, the fifth" |
| "Change **one number** so the tune ends at home." | "Modify the terminal scale index." |
| "Hints are free. They just tell Oak to bring this back sooner." | anything that frames a hint, a rest day or a slow day as a loss |

Rules:

1. Degrees are written 1-based with ♭/♯ (`1 2 ♭3 ♯4`); in code the bridge is always stated the same way: "`n` counts from 0, so degree 5 is `n` 4".
2. Singing copy uses **numbers** ("sing one, three, five") until U03.L08 introduces syllables; after that, syllables with numbers still shown.
3. Chord names in prose use the lead-sheet form (Cmaj7, Cm7♭5); code uses the STYLE spelling (`C^7`, `Cm7b5`). When both appear, show both once: "`C^7` (Cmaj7)".
4. Feedback says **where and how many** first ("2 notes differ, bars 2 and 4"). The catalog template usually suffices; override `feedbackText` only to add the lesson's own image.
5. Pass copy (`onPass` prose in the MDX step) names what the learner just did and, if a term is introduced, bolds it once.
6. Never claim the app or the tutor heard the learner's audio beyond what the mic grader measured. Mic copy: "Your voice is analysed live on this computer. Nothing is recorded or sent."
7. No guilt, no streak talk, no countdowns, no "you should". No emoji. Sentence case in titles and buttons.
8. Titles are 2–4 words and concrete ("Count to Four", "Hear the Bass First").
9. Do not mention unlock mechanics in lesson prose; the Coda announces unlocks.

## 5. Views, notation and scaffold fading

1. Every pitched concept is shown in the linked views (code ↔ roll ↔ staff), but **not all at once early on**: in U00–U04 a step enables at most two of roll, staff and keyboard. Pick the two that serve the step.
2. Notation is rendered from code by the notation engine. Never hand-write ABC. Any example you want notated must render with `approximate = false`; declare `swing` and `pickup` metadata where they apply (contracts §6.10, §6.11).
3. Staff reading is practised daily by the generated "Read it" family and once per unit by your "Play from the page" step.
4. Default scaffolds per unit (set `StepUi` only to deviate, and say why in a comment):

| Units | Roll labels | Roll colour | Staff | Note colour on staff | Degree lyrics | RN under staff |
|---|---|---|---|---|---|---|
| U00 | none | by part | hidden | — | — | — |
| U01 | drum lanes | by part | percussion + counts | — | — | — |
| U02 | note names | by letter name | treble from U02.L04 | on (by letter name) | — | — |
| U03–U04 | note names in U03.L01; degrees from U03.L02 (+ syllables from U03.L08) | by letter name in U03.L01; by degree from U03.L02 | treble | on | on, from U03.L02 | — |
| U05 | degrees | degree / chord tone | grand | on | on | — |
| U06 | degrees | degree + chord band | grand / lead | on hover only | on | from U06.L02 |
| U07 | degrees | learner's choice | lead sheet | off | on hover only | on |
| U08–U10 | degrees | learner's choice | lead sheet | off | off | on |
| U11 and later, advanced | learner's choice | learner's choice | lead sheet | off | off | off |

## 6. Terms

1. Introduce a term only **after** the learner has heard or used the thing. It appears in bold exactly once, in the pass text of the step where it is named, and is declared in `lesson.ts` as `terms: [{ id: 'term.cadence', step: 'S4' }]`.
2. At most three per lesson. If you need a fourth, the lesson has two ideas.
3. Every term gets a glossary entry in `content/terms.ts`: a one-sentence definition in sound-first words, one audio example (code), the lesson that introduces it.
4. **Glossary, not card, by default.** A term becomes a spaced-repetition fact card only if a later lesson tests it: `card: { testedIn: 'U06.L07' }`. CI checks that lesson exists and uses the term in a graded step.
5. Never put a not-yet-introduced term in a prompt, a hint or a feedback override. Hints may use any term introduced in earlier lessons or earlier in this lesson.
6. The tutor receives the introduced-terms list and treats everything else as a preview; your lesson's `terms` are what make that list correct.

## 7. Band layer and flavour kits

1. From U01 every Make declares a Band (`ui.band`), so a two-bar idea sounds like part of a song. Pick an existing `content/bands/*.ts` entry before writing a new one.
2. Band code is read-only for the learner and may use locked tools (it is a preview context). It must follow STYLE, pass the strict lint, and exist for every shipped flavour.
3. The Band supplies the roles the learner is **not** writing. If the Make is a melody, the Band is drums + bass + chords; if the Make is a groove, the Band is bass + chords.
4. A check that needs harmony under a learner melody names the Band track explicitly (`harmony: 'band.chords'`).
5. A flavour changes sounds and the Band, **never the rubric and never the notes the learner must write**. Declare starter sound swaps in `flavours`; ship a passing solution test for each shipped flavour. A swap applies to learner-editable code only where that sound is already unlocked; otherwise the default (`piano`, `ebass`, the default kit) stays, and only the Band carries the flavour's sounds (contracts §5.10 rule 8).
6. The jazz-soul Band uses seventh chords and swing from U03 on; your prose must not name those ideas before their lessons. "Hear how the band leans back" is fine; "swing" as a term waits for U11 (the U01.L09 preview calls it a feel and does not add a term).
7. Use `band: false` only when silence around the part is the point; give the reason in a comment.

## 8. Exercise authoring checklist

For **every** exercise:

- [ ] `id` is a stable slug; `version` starts at 1 and is bumped only when grading semantics change.
- [ ] `skills` use node IDs or node categories from `content/skills.ts`; weights say what the step really tests.
- [ ] `prompt` asks for one thing. A learner who has done only the earlier lessons can do it.
- [ ] `hints` is the fixed tuple **[nudge, pointer, partial, reveal]** (contracts §5.3): a conceptual question → the place and the concept → one issue solved or the same idea in another key → `'auto'`. No hint uses a term not yet introduced. No hint below rung 4 contains the answer. (`hints: null` only for predict, listen and checkpoint items.)
- [ ] Every code string follows STYLE and uses only tools unlocked at or before this lesson; tools this lesson itself unlocks are usable from its first step (or the example is `preview: true` and read-only).
- [ ] You evaluated every code string and looked at the events. Four mistakes make no error and no silence, so only the events show them (STYLE §5.2, §5.3, §11): a chord in a dictionary that voices it wrongly (`Caug` in `triads`); `.n()` written after `.voicing()`; a fraction inside a string time argument (`.late("1/16")`); a control pattern whose values do not line up with the steps (`"1 .35 .6 .35"` over sixteen hats).
- [ ] `tests` are present (below).

For **code kinds** (`code-modify`, `code-fill`, `error-hunt`, `parsons` with code, `dictation` answered in code):

- [ ] At least one reference solution in `reference.solutions`; `[0]` is the canonical one and the hint-4 reveal. Every solution must grade 1.0.
- [ ] **At least one passing test that is not the reference** (an equivalent answer written differently: another octave if the matcher is octave-free, `bd*4` for `bd bd bd bd`).
- [ ] **At least two known-wrong variants, each expecting a different feedback code**: the realistic mistakes for this step (the off-by-one `n`, the unchanged starter, the right rhythm displaced, the missing `.scale()`, the right notes in the wrong octave). `expect: 'fail'`, `feedback: ['melody.index-shift']`.
- [ ] The starter itself fails (a test with the unchanged starter expecting `code.unchanged`).
- [ ] The matcher is the loosest one that still tests the idea: `transposition-invariant` when any key is fine; `pcset` for anything voiced; `rhythm` when pitch is free. Never compare text.
- [ ] Constraints (`must-use`, `max-changed-tokens`, `tempo`) only where the idea needs them, each with a feedback code.
- [ ] If values are randomized, they are `params` with a seeded generator, referenced as `{{param:x}}` / `{ param: 'x' }`; tests pin `params`.
- [ ] Exact-match steps avoid randomness in the code (`?`, `degradeBy`, …).

For **Make** steps:

- [ ] Exactly one `required: true` rule: the lesson's concept. Everything else is a suggestion.
- [ ] Tests: one minimal passing sketch, one rich sketch that goes beyond the brief and still passes, one sketch that breaks the required rule and fails with `rubric.unmet`.
- [ ] The starter already plays something and already nearly meets the rule, so the first Run is a success.
- [ ] No rule depends on singing or tapping.

For **ear, sing, tap** steps:

- [ ] Stimuli come from a family generator (`stimulus: { src: 'generator', family, level }`) unless the lesson needs a fixed example.
- [ ] `sing` declares `fallback`; tolerance is `cents: 'learner'`; tap tolerance is `windowMs: 'auto'`.
- [ ] Sung targets are degrees or stimulus-relative, so the engine can fold them into the learner's range.

What CI adds on its own: **auto-mutants** (five single-token mutations of the reference must fail) run **only for exact-match kinds**; they are skipped for rubric, Make, compose and any matcher with a pass threshold below 1. **Listen QA** covers shown examples and reference solutions only, not starters and not wrong variants.

A skeleton that shows the shapes (illustrative feedback codes; the grader decides the real ones when you run the check):


## 9. Checking and review

### 9.1 `bun run content:check <id>`

`<id>` is a lesson, checkpoint or capstone ID, a unit ID (`U06`), or `all`. `bun run content:build` regenerates `content/.generated/` (IDs, index, toolbox, examples, tutor syllabus) and must be run after adding or renaming anything. The check runs, in this order, and prints the first failure of each kind with the step ID:

1. **Schema**: `lesson.ts` validates against the contract types; folder name matches the ID; every `<Step id>` in the MDX has a step and the reverse; MDX has no code fences.
2. **IDs**: every skill, family, tool, sound, term, can-do, band and song ID exists; none is duplicated or retired.
3. **Map**: `introduces` and `practises` match contracts §2; the lesson is in the syllabus.
4. **STYLE lint** (profile `content`, strict) on every code string.
5. **Unlock-before-use**: every tool, sound, scale name, chord family and mini-notation operator in starters, solutions, examples and required rules is unlocked at or before this lesson in every legal order (contracts §3.1 rules 10–12, §7.6), unless the example is `preview: true`. Flavour starter swaps are checked the same way.
6. **Evaluation**: every example, starter and solution evaluates headlessly with no console error, is not silent, and has a tempo line.
7. **Grading**: every reference solution scores 1.0; every test meets its `expect`, score range and feedback codes; code kinds have ≥ 1 non-reference pass and ≥ 2 fails with distinct codes; auto-mutants fail (exact-match kinds).
8. **Hints**: four rungs present; highlight ranges inside the code; no solution literal in rungs 1–3.
9. **Notation**: every notated example renders to ABC with `approximate = false` and no abcjs warnings.
10. **Sounds**: every sound is in the pack; every control is `audible: true`.
11. **Budget**: scaled minutes, step count, graded checks, terms, panels, split halves (§3).
12. **Make**: exactly one required rule; a Band is declared; a passing test per shipped flavour.
13. **Theory**: declared keys match `.scale()` usage; chord symbols, Roman numerals and answers are re-derived with `@oak/theory`.

`bun run check` runs the same suite for all content, plus the SRS load simulation, which must stay green when you add a family, deck or term card.

### 9.2 Checklist for the music-theory reviewer

Work adversarially: assume each claim is wrong until you have re-derived it with the theory CLI (`bun run theory <op> …`) or by evaluating the code.

- [ ] Every note, interval, chord, Roman numeral, cadence name and key named in prose, hints, feedback and answers is correct **for the code shown**, in the declared key. Check spellings (each letter once in a scale; F♯ not G♭ in G major).
- [ ] Every "this sounds like …" claim is true of the evaluated events, not of the author's intention. Evaluate; do not read the mini-notation by eye.
- [ ] `n` values and stated degrees agree (degree = `n` + 1); chromatic step strings follow STYLE §6.
- [ ] Chord symbols resolve in the dictionary used and are not ✗ cells of STYLE §5.2; voiced chords contain the pitch classes the prose says they contain. A chord's name is checked against its symbol, not guessed from a rootless or two-note voicing.
- [ ] In a piece with sections, each section's length is a multiple of its pattern's length, and any key change is written after `arrange()` (STYLE §9, §10).
- [ ] Before U07.L08 no example or tune starts with a pickup; before U13.L03 none needs a tie or a dot (contracts §2.8).
- [ ] Cadence, function and schema labels use Oak's vocabulary (contracts feedback and schema lists) and are right for the bars named.
- [ ] Terms are introduced after their sound, at most three, each once; nothing later-taught is used earlier.
- [ ] The reference solution is the most natural answer, not a trick; the "equivalent" passing test really is musically equivalent.
- [ ] The Make's required rule tests the lesson's idea and cannot be met by accident or failed by good music.
- [ ] Repertoire: title, year, public-domain status and provenance are right; the answer key matches the cited source; no modern arrangement, no lyrics from a non-PD text.
- [ ] Swing, meter, tempo unit and pickup metadata match the code and the notated result.
- [ ] Nothing in the lesson contradicts contracts or STYLE (conventions are not re-litigated in lessons).

Report each finding with the step ID, the claim, the evidence (CLI output or events) and a proposed fix.

### 9.3 Checklist for the playtest agent

You are a learner who has completed exactly the lessons before this one. You may use only tools unlocked so far and only terms introduced so far.

- [ ] Solve every step from the prompt alone, then with hint 1, hint 2, hint 3. Record the first rung at which the step became solvable. A step that needs rung 3 for a first-time learner is too hard or under-explained.
- [ ] Try the two most likely mistakes on each graded step; confirm the feedback names the place and helps. Report any pass that should fail and any fail that should pass, with the code.
- [ ] Try a correct answer written differently from the reference (other sound, other octave, `*` versus repetition). It should pass unless the prompt forbade it.
- [ ] In the Make: submit the starter unchanged, a minimal answer, and an ambitious answer that goes beyond the brief. The ambitious one must not be marked wrong.
